# infinita-tenders

Агент за обществени поръчки на **Infinita OOD** — автоматизира откриването, класификацията и подготовката на оферти за медицинско оборудване.

## Защо

Обществените поръчки са 80% рутина: следиш портал → четеш спецификации → проверяваш дали имаш подходящ продукт → подготвяш оферта → следиш срокове. Този проект поема рутината; човек влиза само на ключовите решения и финалното подаване (което изисква **КЕП** в ЦАИС ЕОП → остава ръчно).

## Архитектура — конвейер от 4 агента

```
[Cron 07:00]
   │
   ▼
1. DISCOVERY  → TED API търси по 10 CPV кода → дедупликация → db (статус NEW)
   ▼
2. CLASSIFIER → Claude чете спецификацията + мач срещу каталога → score → RELEVANT/SKIP
   ▼
3. DOCUMENTER → за RELEVANT: чернова оферта + таблица за съответствие   (Фаза 3)
   ▼
4. DEADLINES  → напомняния T-7/T-3/T-1 през Resend                       (Фаза 4)
```

## Източници на поръчки

| Източник | Статус | Роля |
|---|---|---|
| **TED API** (`sources/ted.js`) | ✅ работи | Основен поток + готови BG PDF/XML документи |

## Достъп и работа (как се пуска)

Приложението е **2 части**: backend (API на :4010) + frontend (дашборд на :5173). Трябват **2 терминала**.

```bash
# Терминал 1 — backend
cd backend
cp .env.example .env       # TED работи без ключ; добави ANTHROPIC_API_KEY за classify/document
npm install
npm start                  # API на http://localhost:4010

# Терминал 2 — frontend (дашбордът)
cd frontend
npm install
npm run dev                # отвори http://localhost:5173
```

➡️ **Отвори http://localhost:5173** в браузъра — това е дашбордът.

### Работа от дашборда
- **Табове**: Нови / Релевантни / С чернова / Пропуснати — фунията от поръчки.
- **Бутони горе**: „Открий" (нов TED скан) · „Класифицирай" (оценка с Claude) · „Чернови" (генерира предложения).
- **🔔 Банер**: поръчки със срок до 14 дни.
- **📄 Досие**: отваря пълния BG PDF в TED. **📝 Чернова**: преглежда генерираното предложение.

### CLI (без дашборд)
```bash
cd backend
npm run discover          # само откриване (без ключове)
npm run classify          # оценка (нужен ANTHROPIC_API_KEY)
npm run document          # чернови за релевантните
npm run pipeline          # пълен цикъл discover→classify→document→deadlines
npm run cron              # дневен конвейер 07:00 (остави го да върви)
npm run classify:dry      # виж prompt-а без ключ
npm run export-catalog    # презареди каталога от Odoo TEST
```

### Email напомняния (по избор)
Добави `RESEND_API_KEY` + `ALERT_EMAIL` в `backend/.env` → `deadlines` праща дневно резюме.

## Деплой (Railway — 2 услуги)

Repo: `IVUSsky/infinita-tenders` (private). Същият модел като Skyrent/infinita-logistic.

**Backend услуга** (Root Directory = `backend`):
- Build/Start идват от `backend/railway.toml` (`npm install` → `npm start`).
- Env променливи: `ANTHROPIC_API_KEY`, `ENABLE_CRON=true`, `CRON_SCHEDULE=0 7 * * *`, по избор `RESEND_API_KEY`+`ALERT_EMAIL`.
- **Прикачи Volume** на `/data` и сложи `DB_PATH=/data/db.json`, `DRAFTS_DIR=/data/drafts` — иначе данните се губят при всеки деплой.
- `data/catalog.json` се качва в repo-то (нужен на Railway); презареждай го локално с `npm run export-catalog` и push.

**Frontend услуга** (Root Directory = `frontend`):
- Build: `npm install --include=dev && npm run build` → Start: `serve -s dist`.
- Env: `VITE_API_URL` = публичния URL на backend услугата.

> Бележка: подаването на оферти остава ръчно (КЕП в ЦАИС ЕОП) — деплоят автоматизира само откриване/класификация/чернови/напомняния.

## Пазарен анализ (назад във времето)

Модулът досега гледаше само НАПРЕД — какво да офертираме. Разделът „Пазарен анализ“ гледа НАЗАД: кой е
спечелил, на каква цена, срещу колко оферти, и каква марка стои зад доставчика.

**Как работи:** `backend/src/analytics/market.js` тегли обявленията от TED (тесните CPV кодове за ултразвук
*плюс* общите 33000000/33100000, защото около половината ехографи се кодират там), сваля XML-а на всяко
обявление, разчита го на ниво **обособена позиция** и консолидира обявлението за поръчката с обявлението за
решението по идентификатора на процедурата. Един ред = една обособена позиция, не цяла поръчка.

**Команда:** `npm run market` (по избор `npm run market -- 2025-10-01 2026-10-20`). Пълен цикъл ≈ 2 минути;
XML-ите се кешират в `data/notice-xml/`, затова следващите пускания са бързи.

**API:**
- `GET /api/market` — обобщенията (показания, доставчици, възложители, ценови нива, брой оферти, квартали)
- `GET /api/market/rows?class=APARAT&status=Отворена&winner=...` — редовете
- `POST /api/market/refresh` — преизчислява на заден план (`{from,to}` по избор)
- `GET /api/market/status` — тече ли преизчисляване и кога е правено последно

**Три капана, на които стъпва кодът (научени по трудния начин):**
1. **Валутата се чете за всяко поле поотделно, не по датата.** В обявления от 2026 г. прогнозната стойност
   може да е в ЛЕВА, докато офертата е в ЕВРО. Конверсия „по дата“ завишава такава позиция 1,96 пъти.
2. **Стойността идва от офертата, не от обобщението по позицията.** `LotResult/LowerTenderAmount` понякога
   съдържа МЕСЕЧНА такса вместо обща стойност на договора (видяно: 344 € вместо 8 260 €).
3. **TED връща HTTP 200 с празен списък при натоварване.** Празен отговор на първа страница се повтаря,
   иначе тихо изчезват цели групи обявления.

**Класификация:** позициите се разделят на доставка на ехограф / сервиз / консуматив / друг апарат /
смесена / нерелевантна. Правилата са в `market.js`, а ръчно проверените случаи — в
`backend/src/analytics/overrides.json` с ключ `"<обявление>|<позиция>"`. Ключът НЕ е номер на ред: номерата
се местят при всяко разширяване на извадката и мълчаливо залепват чужда класификация.

**На Railway:** сложи `DATA_DIR=/data` (или `MARKET_PATH=/data/market.json`), за да лежи резултатът на
Volume-а. Без това анализът се губи при всеки деплой и трябва да се преизчислява.

**Какво НЕ се вижда:** поръчките под праговете по чл. 20, ал. 3 ЗОП не се публикуват в TED, а само в
ЦАИС ЕОП — по измерване липсват около 25–30% от позициите и 15–20% от стойността, предимно дребни апарати.
Отворените данни на АОП (data.egov.bg, org_id 502) ги съдържат, но в OCDS формат чак от 15.01.2026.

## Един адрес за дашборда и API-то

Дашбордът и backend-ът са две услуги в Railway, но навън трябва да се вижда **един URL**. Затова
`frontend/server.js` раздава готовия интерфейс от `dist/` и препраща `/api/*` към backend-а. Браузърът
говори само с един адрес и няма cross-origin заявки.

**Променливи на frontend услугата:**
- `API_ORIGIN` = адресът на backend услугата, без наклонена черта накрая. На Railway за предпочитане е
  вътрешният адрес `http://<име-на-услугата>.railway.internal:<порт>`; публичният URL също работи, само
  минава през интернет.
- **`VITE_API_URL` трябва да се МАХНЕ.** Тя се вгражда при build и кара интерфейса да бие по абсолютен
  адрес към другата услуга — точно това, което премахваме. Без нея заявките тръгват към същия адрес.

Старт: `npm start` (вече `node server.js`, не `serve -s dist`). Проверка: `GET /healthz` връща към кой
backend сочи проксито. Таймаутът на проксито е 10 минути, за да издържи `POST /api/market/refresh`.

Локално нищо не се променя: `npm run dev` си ползва vite proxy-то към :4010.
